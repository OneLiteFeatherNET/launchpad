## The repository boundary

`queryCollection` runs in exactly one app file: `utils/content/nuxtContentAdapter.ts`.
Everything else — composables, pages, components — goes through
`useContentRepository()` (`composables/useContentRepository.ts`), which returns the
`ContentRepository` interface declared in `utils/content/repository.ts`. Adding a
content type touches, in this order: `content.config.ts` → `utils/content/repository.ts`
(interface) → `utils/content/nuxtContentAdapter.ts` (implementation) → a composable →
a component/page. The one exception is Nitro server routes, which query directly
via a different import — see "Two call signatures" below.

Collection keys are `<name>_<locale>` with an **underscore**, generated by
`defineLocalizedCollections()` in `utils/content/collections.ts` (e.g. `blog_de`,
`blog_en`). Always call repository methods inside `useAsyncData` so the query
resolves during SSR and each collection's dump is fetched once, not per component.

## The schema is a DDL, not a validator

The zod schema on a collection compiles directly into that collection's SQLite/D1
table columns. A frontmatter key the schema doesn't declare is not rejected and not
type-checked — it silently lands in the catch-all `meta` JSON column, so
`doc.thatField` reads `undefined` and `.where('thatField', ...)` fails with
"no such column". `.passthrough()` on the zod object stops parsing from rejecting
extra keys; it does not create columns for them.

Live example in this repo: `blogSchema` in `content.config.ts` does not declare
`releaseDate`, yet `composables/useBlogContent.ts:12` reads `entry.releaseDate` and
`types/blog.ts:46` types it as `releaseDate?: string | Date` — added by hand to the
`BlogArticle` type, outside the generated collection schema. The field compiles and
type-checks, but `entry.releaseDate` is always `undefined` at runtime; the
release-gating logic silently falls back to `pubDate`. That's this rule exactly:
a field can look wired up and still never reach the database. (This is a real,
open defect — out of scope to fix here.)

## `path` is derived, not chosen

For a `type: 'page'` collection, `path` is not the `slug` frontmatter field and not
the app's real route — it's generated purely from the file's location under
`source`. A bare glob keeps the whole matched path: `source: 'blog/${locale}/**/*.md'`
turns `content/blog/en/dev-blog-1.md` into `path: '/blog/en/dev-blog-1'`, unrelated
to the actual i18n-prefixed route `/en/blog/dev-blog-1-what-we-using`, built from
the `slug` field via `pages/blog/[...slug].vue` — note the filename here doesn't
even match `slug`.

`@nuxtjs/sitemap`'s `content:file:afterParse` hook (added by `asSitemapCollection`)
defaults every entry's `loc` to `content.path`, and its content-URL route keeps any
entry where `sitemap IS NOT NULL` — an *unset* `sitemap:` frontmatter field still
passes that check with the broken default `loc`, it is not excluded. In this repo,
every German blog post's frontmatter carries a hand-written
`sitemap: { loc: '/de/blog/<slug>', ... }` override that happens to be correct; no
English post has one, so English posts fall back to the broken derived `path` —
that's why they read as "missing" from `sitemap.xml`.

`source: { include, prefix }` only realigns the locale segment of the derived
`path` — it can't fix a `loc` when a file's `slug` differs from its filename (true
for 2 of the 7 English posts here). For that, use `asSitemapCollection`'s `onUrl`
hook instead of hand-writing frontmatter per file:
`asSitemapCollection(collection, { name: 'blog_en', onUrl: (url, entry) => { url.loc = \`/en/blog/${entry.slug}\` } })`.
It runs once per collection and computes every entry's real `loc` from that entry's
own fields, so no file can be missed the way per-file `sitemap:` can. Use
`type: 'data'` for content that has no URL at all (`team`, `sponsors` already do).

## Two call signatures

- **App** (composables, pages, components): auto-imported, `queryCollection('blog_en')`,
  no event argument. Must run inside the Nuxt app context — wrap it in `useAsyncData`.
- **Nitro** (`server/`): `import { queryCollection } from '@nuxt/content/server'`, then
  `queryCollection(event, 'blog_en')` — the H3 `event` is required as the first
  argument. See `server/api/__sitemap__/team.ts` for the real pattern.

Using the app import on the server, or vice versa, fails or silently resolves nothing.

## Module order

`@nuxtjs/sitemap` and `@nuxtjs/seo` must load before `@nuxt/content` in `modules: []`
(this repo's `nuxt.config.ts` already orders it correctly). Reverse it and
`@nuxtjs/sitemap` warns "you have loaded `@nuxt/content` before `@nuxtjs/sitemap`" and
`asSitemapCollection`/`asSchemaOrgCollection` never get to extend the collection
schema. Full module array: see the `nuxt-seo` skill.

## Indexes

`defineCollection({ ..., indexes: [{ columns: ['slug'] }] })` emits
`CREATE INDEX IF NOT EXISTS idx_<collection>_<col> ON <table> (<col>)` at build time.
None of the current collections declare one. Add an index for every column used in
`.where()` or `.order()` — `slug` and `translationKey` on `blog_*`, `order` on
`faq_*`/`team_faq_*`. On Cloudflare D1 an unindexed `.where()` scans every row on
every request; better-sqlite3 in dev is fast enough that the cost stays invisible
until it ships.

## Verify

Loop until the generated SQL actually matches what `content.config.ts` describes:

1. `pnpm build`
2. Decode the dump for the collection you changed (it's gzip+base64, not plain SQL):
   `node -e "console.log(require('zlib').gunzipSync(Buffer.from(require('fs').readFileSync('.output/public/__nuxt_content/blog_en/sql_dump.txt','utf8'),'base64')).toString())"`
3. Read the output. Check the `CREATE TABLE` line for every column you expect (a
   missing one means the schema doesn't declare it — see "The schema is a DDL"),
   the `path` values against real routes (see "`path` is derived, not chosen"), and
   any `CREATE INDEX` statements you added.
4. If a column, path, or index is missing or wrong, fix `content.config.ts` and
   rebuild. Repeat from step 1 until the dump matches.
