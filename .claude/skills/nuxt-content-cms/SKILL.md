## The repository boundary

`queryCollection` runs in exactly one app file: `utils/content/nuxtContentAdapter.ts`.
Everything else — composables, pages, components — goes through
`useContentRepository()` (`composables/useContentRepository.ts`), returning the
`ContentRepository` interface in `utils/content/repository.ts`. Adding a content
type touches, in order: `content.config.ts` → `repository.ts` (interface) →
`nuxtContentAdapter.ts` (implementation) → a composable → a component/page. The one
exception is Nitro server routes — see "Two call signatures" below.

Collection keys are `<name>_<locale>` with an **underscore**, generated by
`defineLocalizedCollections()` in `utils/content/collections.ts` (`blog_de`,
`blog_en`). Always call repository methods inside `useAsyncData` so the query
resolves during SSR and each dump is fetched once, not per component.

## The schema is a DDL, not a validator

The zod schema compiles directly into that collection's SQLite/D1 table columns. A
frontmatter key the schema doesn't declare is not rejected and not type-checked —
it lands in the catch-all `meta` JSON column, so `doc.thatField` reads `undefined`
and `.where('thatField', …)` fails with "no such column". `.passthrough()` stops
parsing from rejecting extra keys; it does not create columns for them.

Live example: `blogSchema` doesn't declare `releaseDate`, yet
`composables/useBlogContent.ts:12` reads `entry.releaseDate` and `types/blog.ts:46`
types it as `releaseDate?: string | Date` — hand-added to `BlogArticle`, outside the
generated schema. It compiles and type-checks but is always `undefined` at runtime,
so release gating silently falls back to `pubDate`. (Real, open defect, out of scope.)

## `path` is derived, not chosen

For a `type: 'page'` collection, `path` is neither the `slug` frontmatter field nor
the app's real route — it comes purely from the file's location under `source`. A
bare glob keeps the whole matched path: `source: 'blog/${locale}/**/*.md'` turns
`content/blog/en/dev-blog-1.md` into `path: '/blog/en/dev-blog-1'`, unrelated to the
real route `/en/blog/dev-blog-1-what-we-using`, built from `slug` via
`pages/blog/[...slug].vue` — the filename doesn't even match `slug`.

`@nuxtjs/sitemap` registers a `content:file:afterParse` hook **unconditionally**
whenever `@nuxt/content` v3 is present, defaulting every entry's `loc` to
`content.path`. What `asSitemapCollection` does is extend the schema with the
`sitemap` field — that field is the gate: the content-URL route only considers
collections whose manifest declares it, then keeps any entry where
`sitemap IS NOT NULL`. An *unset* `sitemap:` frontmatter field still passes, with
the broken default `loc`. Here every German post carries a hand-written
`sitemap: { loc: '/de/blog/<slug>', … }` that happens to be correct and no English
post does — which is why English posts read as "missing" from `sitemap.xml`.

`source: { include, prefix }` only realigns the locale segment of the derived
`path` — it can't fix a `loc` when a file's `slug` differs from its filename (true
for 2 of the 7 English posts). Use `asSitemapCollection`'s `onUrl` hook instead:
it runs once per collection and computes every entry's `loc` from that entry's own
fields, so no file can be missed.

**`onUrl` must be fully self-contained.** `@nuxtjs/sitemap` serialises it with
`fn.toString()` into the Nitro virtual module `#sitemap/content-on-url`, so the
body is re-evaluated in a scope holding *nothing* from `content.config.ts`.
Closing over anything — a `const`, an import, a `defineLocalizedCollections`
callback parameter — compiles fine, then throws `ReferenceError` when
`/__sitemap__/nuxt-content-urls.json` renders. That bites immediately here: blog
collections come from `defineLocalizedCollections('blog', (locale) => …)`, so the
natural fix closes over `locale`. Derive it instead:

```ts
// content.config.ts — inside defineLocalizedCollections('blog', (locale) => …)
asSitemapCollection(asSchemaOrgCollection({ type: 'page', source: `blog/${locale}/**/*.md`, schema: blogSchema }), {
  name: `blog_${locale}`,                       // evaluated now — fine
  onUrl: (url, entry, collection) => {          // stringified — no outer scope
    const loc = collection.split('_').pop()     // 'blog_en' → 'en'
    url.loc = `/${loc}/blog/${entry.slug}`
  }
})
```

`onUrl`'s third argument is the collection name (typed `collection: string` in
`@nuxtjs/sitemap/dist/content.d.mts`); it and `entry`'s own fields are the only
inputs the stringified body can rely on. Use `type: 'data'` for content with no
URL at all (`team`, `sponsors` do).

## Two call signatures

- **App** (composables, pages, components): auto-imported, `queryCollection('blog_en')`,
  no event argument. Must run inside the Nuxt app context — wrap it in `useAsyncData`.
- **Nitro** (`server/`): `import { queryCollection } from '@nuxt/content/server'`, then
  `queryCollection(event, 'blog_en')` — H3 `event` first. See `server/api/__sitemap__/team.ts`.

Using the app import on the server, or vice versa, fails or silently resolves nothing.

## Module order

`@nuxtjs/sitemap` and `@nuxtjs/seo` must load before `@nuxt/content` in `modules: []`
(`nuxt.config.ts` already orders it correctly). Reverse it and `@nuxtjs/sitemap` warns
"you have loaded `@nuxt/content` before `@nuxtjs/sitemap`", and
`asSitemapCollection`/`asSchemaOrgCollection` never extend the collection schema.
Full module array: see the `nuxt-seo` skill.

## Indexes

`defineCollection({ …, indexes: [{ columns: ['slug'] }] })` emits, at build time,
exactly `CREATE INDEX IF NOT EXISTS idx_blog_en_slug ON _content_blog_en
("slug");` — table `_content_<collection>`, index name
`idx_<collection>_<columns joined by _>`, columns **double-quoted**. A column the
schema doesn't declare is skipped with a `logger.warn`, not an error.

No collection declares an index today. Add one for every column used in
`.where()`/`.order()` in `utils/content/nuxtContentAdapter.ts`: `slug` and
`translationKey` on `blog_*`, **`pubDate` on `blog_*`** (`listBlogArticles`
orders by it), `order` on `faq_*`/`team_faq_*`. On D1 an unindexed `.where()`
scans every row on every request; better-sqlite3 in dev hides that until it ships.

## Verify

Loop until the generated SQL matches what `content.config.ts` describes:

1. `pnpm build`
2. Decode the dump for the collection you changed. It is gzip+base64 of a
   **JSON array of SQL statements**, not newline-separated SQL — parse it:
   ```bash
   node -e "const z=require('zlib'),f=require('fs');JSON.parse(z.gunzipSync(Buffer.from(f.readFileSync('.output/public/__nuxt_content/blog_en/sql_dump.txt','utf8'),'base64')).toString()).forEach(s=>console.log(s))"
   ```
3. Read the statements (each ends in a ` -- <hash>` marker). Check the
   `CREATE TABLE IF NOT EXISTS _content_blog_en` line for every column you expect
   (a missing one means the schema doesn't declare it — "The schema is a DDL"),
   the `path` values in the `INSERT`s against real routes ("`path` is derived"),
   and any `CREATE INDEX` statements you added.
4. If a column, path, or index is missing or wrong, fix `content.config.ts`,
   rebuild, and repeat from step 1 until the dump matches.
